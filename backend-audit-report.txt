BACKEND AUDIT
=============

Scope
-----
Read-only audit of p:\skinConsisus\backend. No application files were modified.


1. EXECUTIVE SUMMARY
--------------------

The backend is an Express/Mongoose monolith using Firebase Admin for
authentication and Gemini for AI.

The current product flow is:

  Admin creates ProductImport
    -> URL is fetched
    -> Gemini extracts product data
    -> Extracted data is stored for review
    -> Admin edits/approves/rejects
    -> Publishing upserts Brand, Category, Ingredients, Product and an
       optional ProductOffer
    -> Product intelligence is generated separately
    -> Product can then be activated/published

Product intelligence is stored embedded inside Product. It is generated once
per product and does not receive SkinProfile data.

Recommendations use deterministic compatibility scoring and optionally use
Gemini to rerank already-selected candidates.

The most important findings are:

  - Product extraction fetches arbitrary HTTP(S) URLs and is vulnerable to
    SSRF without network restrictions.
  - Product edits do not invalidate or regenerate existing intelligence.
  - There is no real research/evidence database.
  - Inactive users are not rejected by authentication middleware.
  - Must-have preference scoring is incorrectly nested inside the
    high-sensitivity branch.
  - Publishing is multi-document and non-transactional.
  - Product intelligence is not generated during publishing.

-----------------------

    - Connects to MongoDB.
    - Mounts all API routes.
    - Adds CORS, JSON parsing, health check and error handling.

Main directories:

  backend/src/middleware/

There is no repository layer. Controllers directly read and write Mongoose
models.

There is no implemented background-job or cron flow.

There is no backend test suite. package.json defines npm test as an
intentional failure command.

Global concerns:

  - CORS defaults to "*" when CLIENT_URL is missing.
  - No rate limiting.
  - No security headers.
  - No request correlation IDs.
  - No transaction handling.
  - Error stacks are exposed outside production.

Import flow:

  POST /api/product-imports
    -> require Firebase authentication
    -> require admin role
    -> validate sourceUrl
    -> create ProductImport(status: pending)

  POST /api/product-imports/:id/extract
    -> load ProductImport
    -> set status to processing
    -> fetch sourceUrl
    -> strip HTML and truncate content
    -> call Gemini extraction
    -> normalize extracted fields
    -> store extractedData, provider, model and raw response
    -> set status to review or failed

  PATCH /api/product-imports/:id/extracted-data
    -> admin can modify extractedData, status and errorMessage
    -> no workflow transition validation

  POST /api/product-imports/:id/approve
    -> status becomes approved
    -> reviewedBy and reviewedAt are stored

  POST /api/product-imports/:id/reject
    -> status becomes rejected
    -> reviewedBy, reviewedAt and errorMessage are stored

  POST /api/product-imports/:id/publish
    -> accepts status approved OR review
    -> validates name, brand and category
    -> upserts Brand
    -> upserts Category
    -> upserts Ingredients
    -> upserts Product with isActive false
    -> optionally upserts Retailer and ProductOffer
    -> sets ProductImport.publishedProduct

Publishing does not generate product intelligence and does not activate the
new Product.

Manual product creation:

  POST /api/products
    -> admin-only
    -> creates Product from supplied existing Brand, Category and Ingredient IDs
    -> does not generate intelligence or quality score
    -> does not automatically create related catalog entities

Manual editing:

  PUT /api/products/:id
    -> admin-only
    -> updates allowlisted product fields
    -> does not clear or regenerate product intelligence
    -> does not recalculate qualityScore

Product deletion:

  DELETE /api/products/:id
    -> permanently deletes Product
    -> does not cascade-delete offers, recommendations, clicks, imports or
       chat references

Product status:

  PATCH /api/products/:id/toggle-status
    -> toggles Product.isActive


4. PRODUCT EXTRACTION AUDIT
---------------------------

File:

  backend/src/services/productExtractionService.js

Input:

  - Product URL
  - Fetched page content
  - Content truncation metadata

Fetching:

  - HTTP(S) URLs accepted.
  - Redirects followed.
  - 20 second timeout.
  - Response body limited to 500,000 bytes.
  - Page text limited to 30,000 characters.
  - HTML tags, scripts, styles and comments stripped.

Gemini extraction fields:

  - name
  - brand
  - category
  - description
  - images
  - ingredients
  - keyIngredients
  - skinTypes
  - concerns
  - fragranceFree
  - alcoholFree
  - price
  - retailer

The import sanitizer additionally supports essentialOilFree and
pregnancyFriendly, but those fields are not declared in the extraction
Gemini schema.

Validation requires:

  - name
  - brand
  - category
  - at least one ingredient

The full raw AI response is stored in ProductImport.aiRawResponse.

Extraction prompt safeguards:

  - Use only information explicitly present on the page.
  - Do not invent ingredients, concentrations or clinical claims.
  - Do not make medical claims or guarantees.

Critical issue:

  Arbitrary URLs can be fetched, including internal/private destinations and
  redirected destinations. No SSRF protection was found.

7. PRODUCT MATCHING AND RECOMMENDATION
--------------------------------------

Authenticated flow:

  POST /api/recommendations/generate
    -> load SkinProfile
    -> load all active Products
    -> populate Brand, Category, Ingredients and keyIngredients
    -> load active ProductOffers
    -> select lowest offer per product
    -> score each product deterministically
    -> remove hard conflicts
    -> apply budget filtering
    -> sort candidates by score
    -> optionally call Gemini to rerank candidates
    -> store Recommendation

Primary implementation:

  backend/src/services/recommendationService.js
  backend/src/services/recommendationScoringService.js
  backend/src/controllers/recommendationController.js

Deterministic score:

  Starts at 50.

Factors include:

  - Skin-type compatibility
  - Brand-listed skin types
  - Concern compatibility
  - Brand-listed concerns
  - Ingredient analysis
  - Sensitivity suitability
  - Hydration profile
  - Oil-control profile
  - Product quality score
  - Offer price and budget
  - Product category
  - Current routine
  - Sunscreen habit
  - Fragrance-free status
  - Alcohol-free status
  - Potential sensitivity ingredients
  - Ingredient conflicts
  - Allergies
  - Avoided ingredients
  - Must-have preferences

Hard conflict behavior:

  - Allergy match caps score at 12.
  - Avoided ingredient match caps score at 30.
  - Conflict/unknown required preferences are filtered out by the
    recommendation service.

Matching and recommendation are partially separated:

  - scoreProductCompatibility is shared by recommendation and anonymous
    analysis.
  - Product intelligence is generated separately and consumed by scoring.
  - Gemini only reranks deterministic candidates.

Known issues:

  - Must-have preferences are ignored for low/medium sensitivity users.
  - Goal scoring is also nested under the high-sensitivity block.
  - Entire active catalog is loaded into memory for each request.
  - Budget handling can behave incorrectly for malformed values.
  - Category filtering can compare caller-supplied values against ObjectIds.
  - Anonymous analysis returns rankedRecommendations instead of the computed
    five-item recommendations array.

14. PRODUCT INTELLIGENCE COMBINATION AUDIT
-------------------------------------------

Product intelligence is generated once per Product, not per SkinProfile.

The system can represent Product x full SkinProfile at matching time, but
does not generate a separate intelligence object for each profile.

Theoretical finite profile combinations, treating multi-select fields as
arbitrary subsets, are approximately:

  5 x 4 x 6 x 5 x 4 x 6 x 2^8 x 8 x 2^14 x 2^5 x 2
  = 1,887,436,800 combinations

This excludes free-form allergies, ingredient database choices, category IDs,
budget values and arbitrary onboardingAnswers.

The test matrix provides:

  - Single-dimension coverage.
  - Pairwise combinations.
  - Safety-critical profiles.
  - Allergy and avoidance cases.
  - Preference cases.
  - Boundary cases.

The matrix is fixture coverage, not proof of production data coverage.

17. CRITICAL RED FLAGS
----------------------

CRITICAL

  1. SSRF in product extraction.
     Arbitrary HTTP(S) URLs, redirects and no private-network restriction.

  2. Stale product intelligence.
     Product edits do not invalidate or regenerate intelligence and quality
     scores.

  3. No genuine research/evidence subsystem.
     AI evidence labels are not independently verified.

HIGH

  4. Inactive users remain authorized.
     protect() does not check User.isActive.

  5. Publishing is not transactional.
     Partial writes can leave inconsistent catalog state.

  6. Preferences are ignored for most users.
     Must-have preference logic is nested under high sensitivity.

  7. Entire catalog is loaded into memory for recommendation requests.

  8. Raw AI responses are persisted in imports.

  9. Product click tracking is public and unthrottled.

MEDIUM

  10. Ingredient deletion leaves dangling references.
  11. Offer updates do not verify replacement references.
  12. Offer URL validation is missing.
  13. Inactive retailers are not excluded from public offer reads.
  14. Import status transitions are not enforced.
  15. Publishing accepts review status in addition to approved.
  16. Anonymous analysis returns rankedRecommendations rather than the
      computed five-item recommendations array.
  17. Chat lacks skincare-specific safety guardrails.

LOW

  18. Embedding fields and vector search are placeholders.
  19. Intelligence versioning is metadata-only, not historical.
  20. Error stacks are exposed outside production.

19. RECOMMENDED ARCHITECTURE BEFORE MODIFICATION
------------------------------------------------

No changes were implemented during this audit.

Recommended future separation:

  - Import domain: fetch, extraction, review, approval and publishing.
  - Catalog domain: Product, Brand, Category, Ingredient, Retailer and Offer.
  - Intelligence domain: generation, versions, metadata and invalidation.
  - Evidence domain: research sources, citations and verification.
  - Matching domain: deterministic safety filters and compatibility scoring.
  - Recommendation domain: candidate generation, ranking and explanations.
  - Publishing workflow: explicit states and transactional writes.
  - Audit/security layer: admin actions, SSRF protection, rate limits and
    inactive-user enforcement.

Product intelligence should be versioned or invalidated whenever relevant
Product fields change.

FINAL CONCLUSION
----------------

If a product and a user profile are supplied today, product selection is
determined by the recommendation scoring path, not by per-user product
intelligence generation:

  SkinProfile
    -> active Product catalog
    -> active ProductOffer prices
    -> scoreProductCompatibility()
    -> allergy/avoidance/preference filtering
    -> budget filtering
    -> deterministic score sort
    -> optional Gemini reranking
    -> Recommendation response

The system has a meaningful deterministic matching foundation, but product
intelligence is universal and can become stale, evidence is not research
backed, and several authorization, consistency and scalability risks should be
addressed before expanding the intelligence architecture.
